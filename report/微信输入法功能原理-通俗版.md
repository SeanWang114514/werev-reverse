# 微信输入法功能原理：通俗版

> 本文是《微信输入法逆向分析报告》的通俗解读，面向第一次接触输入法逆向的读者。
>
> 分析样本以微信输入法 Windows `2.1.4.6` 为主，词库章节结合 `3.0.0.34` 复核。详细证据、函数地址、协议和产物索引见仓库中的主报告。

## 一句话理解

微信输入法不是“一个程序包办所有事情”，而是一套分工明确的组合：

```text
宿主程序（浏览器、微信、Office、记事本等）
        │
        ▼
Windows TSF 输入法层
        │  接收按键、读取光标上下文、显示候选、提交文字
        ▼
wetype_server.exe
        │  常驻中枢：管理会话、词典、网络、剪贴板、同步和上报
        ▼
libwxhld.dll
        │  真正的输入引擎：拼音、五笔、英文、笔画、候选和排序
        ▼
wetype_renderer.exe
            Flutter 界面：候选窗、设置、剪贴板、语音、翻译等
```

可以把它类比成一家公司：

- `wetype_tip_core.dll` 是前台，负责接待 Windows 和用户输入；
- `wetype_server.exe` 是调度中心，负责协调各个部门；
- `libwxhld.dll` 是核心业务部门，负责真正“猜你想打什么”；
- `wetype_renderer.exe` 是展示部门，负责把候选和界面画出来；
- 云端服务是外部顾问，负责增强能力，但不是基础打字的前提。

各进程之间主要使用命名管道、共享内存和 protobuf 通信。

## 二、输入是怎么变成候选的

以输入 `nihao` 为例：

```text
用户输入：n i h a o
        ↓
切成音节：ni + hao
        ↓
查询词库：你、尼、呢、你好、拟好……
        ↓
组成多条候选路径
        ↓
用词频、上下文、用户习惯和语言模型打分
        ↓
显示排序后的候选
        ↓
用户选择后，把这次选择写回用户词典
```

这里最关键的三个部件是：

1. **词典**：知道有哪些字、词、短语和编码；
2. **音节图**：知道一串字母可以切成哪些拼音组合；
3. **排序器**：从大量合法组合中挑出最像人话的结果。

微信输入法不只是“查词”，还会做整句解码、上下文重排和个人学习。

## 三、重要功能与实现原理

| 功能 | 通俗解释 | 主要实现线索 |
|---|---|---|
| Windows 输入法接入 | 先接管键盘，再决定显示候选还是直接把字送进输入框 | TSF、`wetype_tip_core.dll`、组合文本和候选状态 |
| 拼音输入 | 把字母切成音节，再查词并组合成句子 | `PinyinV2Session`、音节图、Trie/大词库、Beam Search |
| 五笔输入 | 按五笔编码查字词，并维护输入会话 | `WubiSessionV2`、五笔用户词典 |
| 英文输入 | 处理英文单词、联想和大小写 | `EnglishSessionV2`、英文模型和词典 |
| 笔画输入 | 按笔画序列查候选字 | `StrokeSession`、`StrokesSearcherV2` |
| 数字输入 | 数字候选、单位、日期等 | `NumberSession`、`NumSequelSearcher` |
| 整句输入 | 不要求先选字，而是把整串拼音切成多条可能路径，再选最像人话的一条 | `SentenceSearcherV3`、`FeatureBuilder`、Beam Search |
| 候选排序 | 不只看词频，还看上下文、用户习惯和语言模型 | `MixRank`、LightGBM、NNLM、XNet、TFLite |
| 云端候选 | 本地先出结果，云端结果太慢就直接丢弃 | 默认约 200ms 超时，云端 AB 参数可调到约 550ms |
| 上下文联想 | 读取光标前、光标后和选中的文字，再推荐相关词 | TSF surrounding text、`TextOnCursorSearcher` |
| 用户学习 | 用户选过哪些词，下次就更靠前 | LevelDB 用户词典、候选点击记录、个人模型 |
| 热词 | 自动发现最近经常输入的新词 | `user_hot_word_detector`、热词词典 |
| 简繁转换 | 在候选阶段把简体结果转换成繁体 | `SimplifiedToTraditional` |
| 敏感词过滤 | 在结果返回前拦截或替换特定内容 | `InterceptSensitiveResult`、敏感词 Trie |
| 符号、颜文字、表情 | 本地符号表和匹配器；微信表情另需微信联动 | `EmojiMatcher`、`PcEmojiMatcher`、`UncommonKaomojiFilter` |
| 计算器 | 识别数字表达式并直接给出结果 | `NumberCalculator` |
| 日历 | 识别日期、节日、节气等 | `Calendar`、内置日历数据 |
| V 模式 | 把计算、符号、剪贴板、常用语、AI 等入口集中起来 | `VModeV2`、`VmodeDataManager` |
| 剪贴板历史 | 保存复制过的文本和图片，供以后选择 | `ClipboardDataManager`、本地存储 |
| 跨设备剪贴板 | 把剪贴板内容同步到其他设备 | 配对码、账号、云端消息、protobuf 同步协议 |
| 文件传输 | 设备之间直接传文件 | 局域网、Wi-Fi Direct、AWDL、gRPC 隧道、双向 TLS |
| 语音输入 | 本地判断什么时候开始和结束说话，云端做识别 | 本地 VAD；识别主要依赖云端 |
| AI 问答 | 输入问题，服务器生成结果 | `WtAskAI` 协议；服务端返回 HTML，界面用 WebView 展示 |
| 翻译 | 把文本发送到服务端翻译 | 网络协议和云端翻译服务 |
| 微信表情联动 | 读取微信表情、发送表情、绑定微信身份 | `WeChatMessageManager`、`WTVerifyToken`、微信 token |
| 词典更新 | 从 CDN 下载新词库、补丁和灰度配置 | `update.proto`、full/patch 更新、AB 实验 |
| 日志和上报 | 记录按键、候选点击、性能、崩溃等 | Sentry、埋点协议、xlog 加密日志 |
| 远程命令框架 | 引擎中存在一组本地 JSON 命令，包括回放输入 | `RemoteCommandExecutor`、`replay_input` |

## 四、核心引擎为什么强

### 1. 本地词库和音节图

拼音输入不是简单地把字母映射到汉字。一个拼音串可能有很多种切分方式，例如：

```text
xian
```

既可能是：

```text
xian  -> 先 / 现 / 线
xi an -> 西安
```

引擎需要同时保留这些可能性，再结合词库和上下文决定哪条路径更合理。

### 2. 整句解码

传统输入法常常先让用户选词，再继续输入。整句输入则会把一整串拼音作为输入，尝试生成多个完整句子候选。

这通常需要：

- 音节切分；
- 词语候选；
- 语言模型；
- Beam Search；
- 候选打分和重排。

### 3. 多模型排序

微信输入法的排序器不是单一规则，而是多种信号叠加：

- 词频；
- 上下文；
- 用户历史；
- LightGBM 树模型；
- 神经网络语言模型；
- TFLite 模型；
- 自研 XNet 推理后端。

可以把它们理解成多个“评委”分别打分，最后综合排序。

### 4. 本地优先，云端增强

核心打字能力在本地完成，断网仍然可以输入。

云端候选只是增强项，而且有严格的超时控制。云端结果如果太慢，会被直接丢弃，避免影响键盘响应。

这意味着：

```text
本地结果 = 基础能力
云端结果 = 可选加分项
```

## 五、上下文联想是怎么工作的

输入法通过 Windows TSF 的 surrounding text 能力，读取宿主程序输入框中的：

- 光标前文本；
- 光标后文本；
- 当前选中文本。

这些信息可以用于：

- 根据前文推荐下一个词；
- 纠正输入；
- 提供更贴合场景的候选。

这也是上下文联想必须付出的隐私代价：输入法进程能够看到宿主程序输入框中的文本片段。

报告中还发现，本机存在明文上下文抓取日志。这不代表内容一定上传，但说明本地确实有敏感数据落盘面。

## 六、语音、翻译和 AI

### 语音输入

可以把语音链路拆成两段：

```text
麦克风 -> 本地 VAD -> 云端语音识别 -> 文本
```

- **VAD**：判断用户什么时候开始说话、什么时候结束；
- **识别**：主要依赖云端服务。

本机确实存在本地 VAD 模型。Dart/UI 层也有“离线语音包”的埋点线索，但现有证据不足以证明已经存在完整的离线语音识别能力。

### 翻译

翻译主要依赖云端服务。输入法负责收集文本、发送请求、接收结果并显示。

### AI 问答

AI 问答也是服务端能力。客户端通过协议发送问题，服务端生成 HTML 或结果，再由 WebView 展示。

因此，断网时这些功能不能完整工作。

## 七、剪贴板、同步和文件传输

### 本地剪贴板历史

输入法会保存用户复制过的文本和图片，形成可搜索、可选择的历史记录。

这部分可以完全本地实现。

### 跨设备剪贴板

跨设备同步需要：

- 设备身份；
- 配对码或账号；
- 云端消息通道；
- 冲突处理；
- 加密和权限控制。

没有服务器时，可以退而求其次，做局域网同步，但无法完整复刻微信的账号级跨设备体验。

### 文件传输

报告里能看到局域网、Wi-Fi Direct、AWDL、gRPC 隧道和双向 TLS 等设计。

其中局域网直连可以自己实现；跨网络、跨账号的设备发现和配对，仍然需要服务端基础设施。

## 八、不借助服务器可以复刻哪些内容

### 1. 很适合复刻，难度中等

这些功能可以完全本地实现：

- Windows TSF 输入法框架；
- 拼音输入；
- 五笔输入；
- 笔画输入；
- 英文输入；
- 数字输入；
- 本地词库、Trie、音节图；
- 候选生成和 Beam Search；
- 本地候选排序；
- 用户词典和学习；
- 热词检测；
- 基于光标上下文的本地推荐；
- 剪贴板本地历史；
- 符号、颜文字、本地表情；
- 计算器；
- 日历、节日、节气；
- 简繁转换；
- 敏感词本地过滤；
- V 模式入口；
- 本地 VAD；
- 局域网或 P2P 文件传输；
- 本地增量词库更新，或者手动下载词库包更新。

如果只是想做一个能用的输入法，最小组合可以是：

```text
Windows TSF
+ librime / Rime
+ 开源拼音词库
+ 本地用户词典
+ 一个候选窗 UI
```

这是最现实、维护成本最低的路线。

### 2. 可以本地做，但效果不会完全一样

- 本地语言模型排序；
- 本地整句输入；
- 本地上下文推荐；
- 本地语音识别；
- 本地翻译；
- 本地 AI 问答；
- 本地表情推荐；
- 本地剪贴板智能分类。

这些功能不是不能做，而是需要自己部署模型：

- 语音识别可以用本地 ASR 模型；
- 翻译可以用本地翻译模型；
- AI 问答可以用本地小模型；
- 候选排序可以训练自己的排序模型。

但要做到微信输入法的速度、准确率、模型体积和中文效果，需要大量数据和工程优化。

### 3. 不借助服务器基本无法完整复刻

这些功能依赖账号、云端或腾讯内部服务：

- 微信账号绑定；
- 微信表情包读取和发送；
- 微信好友和聊天相关联动；
- 腾讯云端候选；
- 云端 AI 问答；
- 云端翻译；
- 云端语音识别；
- 跨设备剪贴板同步；
- 跨设备热词同步；
- 设备配对和账号同步；
- 云端 AB 实验；
- 灰度词库下发；
- CDN 增量词库；
- 云端日志、崩溃上报和埋点统计。

其中有些可以用“局域网 + 自己搭一个轻量服务”替代，例如：

- 局域网剪贴板同步；
- 局域网文件传输；
- 自己的词库更新服务器。

但这已经不是“完全不用服务器”，而是“把腾讯服务器换成了自己的服务器”。

## 九、需要特别注意的技术边界

### 1. 不能把 Mozc 血缘说得过满

现有证据支持部分架构、协议或宿主层存在 Mozc 血缘线索，但不能据此断言“整个拼音算法就是 Mozc”。

### 2. 微信原生大词库还没有完整解码

目前能确认词典文件、部分格式、部分词条和索引，但不能说已经完整迁移了微信词库。

### 3. “离线语音包”只有 UI 和埋点线索

可以确认本地有 VAD，不能据此断言已经存在完整离线语音识别。

### 4. 远程命令框架只证明了本机执行能力

报告发现了 `RemoteCommandExecutor` 和 `replay_input` 等命令，但没有证明公网可以直接触发，不能把它描述成已被远程利用的漏洞。

### 5. 不同版本不能混用结论

旧样本主要是 `2.1.4.6`，当前安装版本是 `3.0.0.34`，核心文件哈希不同。地址、结构和行为细节都可能变化。

## 十、最终判断

微信输入法最重要的能力可以概括为：

> TSF 负责接入 Windows，`libwxhld` 负责本地输入和候选排序，Flutter 负责界面，`wetype_server` 负责进程协调、网络、同步和剪贴板；云端主要提供云候选、AI、翻译、语音识别、微信联动和配置下发。

不借助服务器时，最值得复刻的是：

> 一个基于 TSF + librime/Rime 的本地输入法，包含拼音、五笔、英文、笔画、词库、候选排序、用户学习、热词、上下文推荐、剪贴板历史、符号、计算器、简繁转换和本地 VAD。

不建议一开始追求完整复刻微信的云端能力，尤其是 AI、语音识别、微信表情和跨设备同步。这些需要账号体系和服务端基础设施。
